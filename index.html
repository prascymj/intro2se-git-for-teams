Git for Teams: one shared source of truth

Git is not a cloud folder for uploading files. It is the tool software teams use to share the current version of their work, keep every past version, and show who did what. This page explains why, shows how a real project repository is organised, and gives you steps to fix your repo.

1. The problem2. Why Git3. How sharing works4. Versions = commits5. Branches6. Repo structure7. Good commits8. Fix your repo9. Checklist10. Your team review

01The problem we see in many repos

Many team repositories look like a shared drive: every new version is uploaded as a new file, and the version number is written into the file name. Git already does this job for you, so these copies only make the repo harder to use.

Using Git like a file drive
repo/ M1-Charter ver1.0.pdf copy M1-Charter ver2.0.pdf copy M2_SRS_ver1.0.pdf copy M2_SRS_ver2.0.pdf copy Team(Prototype).pdf index_ver1.0.html which one runs? index_ver1.0.1.html script_ver1.0.js app_ver1.0.1.js style_ver1.0.css style_ver1.0.1.css no README, no folders 7 commits, all "Add files via upload"
Using Git as designed
repo/ README.md what, who, how to open docs/ M1-team-charter.pdf M2-srs.pdf design/ diagrams final-report.md ai-use-statement.md prototype/ index.html one entry point css/style.css js/app.js slides/demo-slides.pdf one file per document, latest version only older versions live in the commit history

What goes wrong with the left side: nobody can tell which file is current; a teammate may edit style_ver1.0.css while the page loads style_ver1.0.1.css; reviewers cannot see what changed between versions; and the history says nothing about who did which part.

For this course: work that is not committed by your own GitHub account cannot be counted as your contribution. Commit your own work, from your own account, with a message that says what you did.

03How Git shares data in a team

Each member has a full copy of the repository on their computer. GitHub holds the shared copy. You pull to get your teammates' latest work and push to share yours.

04Versions are commits, not file names

You never need index_ver1.0.1.html. Keep one file called index.html and commit it each time it changes. Git keeps every version, and you can mark important ones with a tag such as v1.0.

To see or restore an old version: on GitHub open the file and click History, or run git log --oneline index.html, then git show v1.0:prototype/index.html.

05Branches: work in parallel without breaking main

A branch is a separate line of commits. Do a feature on its own branch, ask a teammate to review it in a pull request, then merge it into main. Remember to merge: work left on another branch is not part of your submitted version.

For a small team, a simple rule is enough: main must always open and run. Name branches after the work, for example feature/fr-2-item-list or fix/login-empty-password.

06What a software project repo contains

Professional repositories follow a predictable layout so that anyone, including the grader, can find things in seconds. A layout that fits the Intro2SE project:

team-project/ README.md project name, team members + GitHub accounts, how to open the prototype, links .gitignore files Git should ignore (node_modules/, .DS_Store, build output) docs/ M1-team-charter.md or .pdf; one file, kept up to date M2-srs.md FR and NFR with IDs (FR-1, FR-2, ...) design/ use-case.png sequence-fr-2.png data-model.png final-report.md golden-thread.md FR -> design -> prototype page -> test ai-use-statement.md prototype/ index.html the ONE entry point; opens in a browser pages/ other screens, e.g. login.html css/style.css js/app.js assets/ images, icons slides/ demo-slides.pdf tests/ test cases or test report (optional for M3)

Why Markdown for documents

Git can show line-by-line changes in text files such as .md, .html and .js. It cannot show what changed inside a PDF or DOCX. Write documents in Markdown when you can, and if you must use Word, export one PDF and replace the old one in the same file name. The history keeps the old version.

The README is the front door

When someone opens your repo, GitHub shows README.md first. It should answer: what is this system, who is in the team (name, student ID, GitHub account), how do I open the prototype (for example a GitHub Pages link or "open prototype/index.html"), and where are the documents.

07Good commits

A commit message is a note to your team and your future self. "Add files via upload" tells nobody anything. Write what changed and, when possible, which FR it serves.

Unhelpful
Add files via upload Update index_ver1.0.1.html final fix asdf
Helpful
Add item list page (FR-2) Show error when item name is empty (FR-2) Add sequence diagram for checkout (FR-4) Update SRS: NFR-1 response time 2 s Move prototype files into prototype/
  • Small and often. One idea per commit. Several small commits are easier to review than one huge upload.
  • Your own account. Each member commits their own work. Uploading for a teammate hides their contribution.
  • Uploading on the GitHub website is fine, but replace the default message in the "Commit changes" box with a real one.

08Fix your repo in 15 minutes

You do not lose anything by deleting the old copies. Every version you committed stays in the history.

Option A: command line

# 1. get the latest shared version
git pull

# 2. create folders
mkdir -p docs prototype/css prototype/js slides

# 3. keep ONE current file and give it a plain name (git mv keeps its history)
git mv index_ver1.0.1.html prototype/index.html
git mv style_ver1.0.1.css  prototype/css/style.css
git mv app_ver1.0.1.js     prototype/js/app.js
git mv "Team_M2_SRS_ver2.0.pdf" docs/M2-srs.pdf

# 4. remove the old copies (they remain in history)
git rm index_ver1.0.html style_ver1.0.css script_ver1.0.js "Team_M2_SRS_ver1.0.pdf"

# 5. fix links inside index.html: css/style.css and js/app.js, then test in a browser

# 6. save and share
git commit -m "Reorganise repo: docs/ and prototype/, remove versioned copies"
git push

# 7. optional: mark the demo version
git tag v1.1 -m "M3 demo version"
git push --tags

Option B: GitHub website or GitHub Desktop

  1. Open the current file (for example index_ver1.0.1.html), click the pencil icon, and change the file name box to prototype/index.html. Typing a / creates the folder. Commit with a clear message.
  2. Do the same for the CSS, JS and document files.
  3. Open each old copy, choose Delete file from the menu, and commit.
  4. Edit prototype/index.html so its links point to css/style.css and js/app.js. Open the page to check it still works.
  5. Add a README.md with team members, GitHub accounts and how to open the prototype.
If your team has work on another branch, open a pull request and merge it into main, so the complete version is in one place.

09Checklist before the demo

  • No version numbers or "final" in file names. One file per document.
  • Folders: docs/, prototype/, slides/.
  • The prototype opens in a browser with no server or database needed, and the README says how to open it.
  • README.md lists members, student IDs, GitHub accounts, and how to open the prototype.
  • Final Report with the Golden Thread table, demo slides and the M3 AI-Use Statement are committed.
  • All work is merged into main.
  • Every member has commits from their own account with meaningful messages.
